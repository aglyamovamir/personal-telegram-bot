# Миграция v1: владельцы истории

Текущий код этапа 7 требует готовую **v4**. Содержимое и контракт миграции v1
не изменены; после неё отдельно запускается v2, затем при необходимости перенос
A/B/C. Команды и архитектура программ: [PROGRAMS.md](PROGRAMS.md).
После v2 отдельно выполняется [миграция редактора v3](EDITOR.md).
После v3 отдельно выполняется [миграция необязательных планов v4](SIMPLE_PROGRAMS.md).

В этапе 3 обработчики, планировщик и Google Sheets были переведены на схему v1.
В этапе 7 `init_db()` проверяет уже мигрированную базу v4: версию, обязательные поля,
внешние ключи, уникальность дневных записей, наличие первоначального владельца
и целостность. Старые, отсутствующие и неподдерживаемые базы приводят к понятной
ошибке запуска, без создания таблиц и автоматического переноса данных.
Миграция никогда не запускается автоматически из `init_db()`.
Рабочая база ещё не мигрировалась: сначала нужна репетиция на актуальной копии.

## Схема

- `users`: внутренний `id`, уникальный `telegram_user_id`, nullable
  `private_chat_id`, `timezone` (по умолчанию `Europe/Moscow`), `created_at` в UTC.
- `workouts`: прежние поля и обязательный `user_id REFERENCES users(id)`;
  индекс `(user_id, started_at)`. Незавершённые записи остаются незавершёнными.
- `daily_metrics`: прежние поля и обязательный внешний ключ `user_id`;
  уникальность `(user_id, date)` вместо глобальной уникальности даты.
- `workout_sets`: не меняется; владелец определяется через `workouts`.
- `user_settings`: первичный и внешний ключ `user_id`, утреннее/вечернее время,
  отдельные флаги включения (0/1). Существующее расписание получает только
  первоначальный владелец. При пустых старых настройках новая таблица пуста.
- `bot_settings_legacy`: неизменённые старые настройки, переименованные для
  сохранения всех полей. Это архив, не источник настроек новой архитектуры.
  Старый `chat_id` сохраняется здесь: он мог быть группой, поэтому автоматически
  заполнять им `private_chat_id` небезопасно. Его настройка — следующий этап.
- `schema_migrations`: версия, Telegram ID первоначального владельца, время.
- Каталог упражнений со всеми дополнительными столбцами, включая `image_url`,
  и его дочерние таблицы не перестраиваются и не обновляются.

## Запуск только на отдельной копии

Сначала получить согласованную резервную копию SQLite через Backup API,
сохранить оригинал, создать отдельную рабочую копию. Файл не должен использоваться
ботом или другими процессами. Мигратор сам не делает резервную копию и не может
определить, является ли файл копией. Флаг ниже — явное подтверждение оператора.
Не указывайте путь к локальной базе разработки или `/data/database.db`.

Пример команды из корня проекта (ID — пример, требуется подтверждённый ID владельца):

```powershell
.\.venv\Scripts\python.exe -B -m database.migrations --database "C:\migration-tests\history-copy.sqlite3" --owner-telegram-id 123456789 --confirm-offline-copy
```

Файл должен существовать: ошибка пути не создаст новую пустую БД. `.env`,
`DB_PATH`, `main.py`, Telegram и Google Sheets мигратору не нужны.
Поддерживаемый программный вход: `migrate(path, owner_telegram_id)`.

## Гарантии и ограничения

`BEGIN IMMEDIATE` охватывает создание таблиц, перенос данных и запись версии.
При любой ошибке выполняется rollback. Проверки `integrity_check` и
`foreign_key_check` выполняются перед изменениями и перед commit. Повторный
запуск той же версии и владельца проверяет целостность и ничего не меняет;
другой владелец или неизвестная версия отвергаются.

При перестройке используются исходные объявления столбцов из sqlite_master;
копируются все прежние столбцы, сохраняются ID и значения, пользовательские
индексы и триггеры, а также счётчики AUTOINCREMENT (включая удалённые высокие ID).
Для ожидаемой старой схемы удаляется inline-ограничение `date TEXT NOT NULL UNIQUE`.
Незнакомая форма этого ограничения, отдельные пользовательские уникальные индексы
метрик, частично мигрированная схема или конфликты имён приводят к отказу и откату,
а не к попытке угадать правильное преобразование. Серверную схему надо сначала
проверить на копии. Необычные зависимости представлений/триггеров также могут
потребовать отдельной адаптации.

Для перестройки родительской таблицы проверка внешних ключей временно выключена
только в соединении мигратора до начала транзакции. `foreign_key_check` всё равно
проверяет ссылки явно перед commit. Это не меняет настройки других соединений.
`get_connection()` включает `PRAGMA foreign_keys=ON` для каждого рабочего
соединения. Наличие FK в схеме само по себе недостаточно.

## Реализованный контракт доступа (этап 3)

Все функции личных данных принимают внутренний `users.id` первым аргументом.
Telegram ID используется только для регистрации, авторизации и политики экспорта.

| Функции | Реализованное поведение |
| --- | --- |
| `create_workout` | Обязательный внутренний `user_id` при INSERT |
| `save_set` | В одной транзакции проверить владельца и активность родительской тренировки перед INSERT |
| `finish_workout`, `cancel_workout` | Проверять `id + user_id` и допустимый статус; отмена и удаление подходов атомарны |
| `get_last_workout`, `get_last_workout_by_type` | Обязательный фильтр владельца |
| `get_workout_sets` | JOIN workouts и фильтр владельца |
| `get_last_exercise_sets` | Фильтр владельца во внешнем запросе и вложенном SELECT |
| `has_workout_on_date` | Владелец и корректные границы даты в его часовом поясе |
| `save_morning_metrics`, `save_evening_metrics` | user_id при INSERT и ON CONFLICT(user_id, date) |
| `get_daily_metrics`, `update_daily_metric` | WHERE user_id = ? AND date = ?; список разрешённых полей сохранить |
| `save_user_settings`, `get_user_settings` | API для user_settings с обязательным user_id |
| `get_connection`, `init_db` | FK включены; текущий старт допускается только с проверенной схемой v4 |

`get_or_create_user()` не переназначает историю. Middleware разрешает только
личные чаты пользователей из `ALLOWED_TELEGRAM_IDS`, затем передаёт внутренний
user_id в обработчик. Для callback используется `callback.from_user.id`.
`get_workout`, `get_workout_sets`, сохранение подходов, завершение и отмена
отказывают при чужом ID одинаковой ошибкой. Изменение завершённой тренировки
также запрещено. `save_exercise_sets` сохраняет сообщение одной транзакцией.

Подробности настройки и изменения поведения: [MULTIUSER.md](../MULTIUSER.md).

## Проверки

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -p "test_*.py" -v
```

Все файлы тестовых БД создаются в TemporaryDirectory. Тесты покрывают сохранность,
внешние ключи, отсутствие владельца, одинаковую дату разных пользователей,
повторный запуск, неверного владельца, дополнительные поля, пустые настройки,
счётчики ID, отказ при orphan-записях и полный откат после перестройки таблиц
и при ошибке итоговой проверки. Реальные БД не используются.
