# Программы и снимки тренировок — схема v2

Этап 5 добавил Telegram-конструктор и явную миграцию v3 для архивирования и
ревизий. Текущий старт требует v4. Схема/снимки v2 сохранены; руководство
конструктора и обновления: [EDITOR.md](EDITOR.md).

Этап 7 требует v4: подходы в новых программах необязательны, ID существующих дней
и позиция цикла сохраняются. Актуальная политика: [SIMPLE_PROGRAMS.md](SIMPLE_PROGRAMS.md).

## Разделение плана и факта

Программа — редактируемый план пользователя. День — упорядоченная тренировка
внутри плана, а не день календарной недели. Можно иметь 1, 2, 3, 4, 6 или другое
положительное количество дней. Ограничения частотой «три раза в неделю» нет.

При начале тренировки выбранный день копируется в JSON-снимок версии 1.
Названия, порядок упражнений, внешние exercise_id, разминка и все рабочие
шаблоны берутся только из этого снимка до конца тренировки. Снимок не является
ссылкой на текущую версию плана. Изменение или удаление программы не меняет его.
Плановые подходы никогда не записываются как выполненные.

## Новые таблицы

| Таблица | Назначение |
| --- | --- |
| `programs` | Владелец users.id, название, флаг активной программы, позиция следующего дня |
| `program_days` | Название дня и порядок внутри программы |
| `program_day_exercises` | Отдельное включение упражнения: ссылка на общий exercises.id, пользовательское имя, порядок, число рабочих подходов |
| `program_set_templates` | Упорядоченные плановые разминка/работа; вес и повторения могут быть не заданы |
| `workout_sessions` | Ссылка на workout, JSON-снимок, JSON-прогресс, ревизия; необязательные ссылки на источник |
| `workout_set_occurrences` | Связь фактического set_id с позицией упражнения в снимке; различает повтор одного упражнения |
| `program_imports` | Маркер однократного переноса A/B/C конкретному владельцу |

Уникальный частичный индекс разрешает не более одной активной программы на
пользователя. Неактивных программ может быть несколько. Порядок дней и упражнений
уникален в пределах родителя; само упражнение может повторяться сколько нужно.
Каталог общий и не обновляется этими API.

Миграция v2 не перестраивает и не обновляет существующие workouts/workout_sets,
метрики, настройки или каталог. В schema_migrations добавляется строка версии 2;
строка v1 сохраняется. Код миграции v1 не изменён. У workout_sets не появляется
дублированный user_id: владелец определяется через workouts.

## Явные команды для отдельной тестовой копии

Команды ниже не выполнялись над реальными базами. Сначала получить согласованную
резервную копию и работать с её отдельным экземпляром; бот не должен использовать
этот файл. Миграторы не создают резервные копии автоматически.

Если копия ещё имеет старую однопользовательскую схему, сначала выполнить v1 по
MIGRATIONS.md с подтверждённым Telegram ID владельца. Для уже готовой v1:

```powershell
.\.venv\Scripts\python.exe -B -m database.migrations_v2 --database "C:\migration-tests\history-copy.sqlite3" --confirm-offline-copy
```

Отдельно, при необходимости перенести старую A/B/C:

```powershell
.\.venv\Scripts\python.exe -B -m database.import_legacy_program --database "C:\migration-tests\history-copy.sqlite3" --owner-telegram-id 123456789 --confirm-offline-copy
```

Владелец сверяется с записью миграции v1. Другой пользователь получает отказ.
При отсутствии упражнения в каталоге перенос целиком откатывается. Новые
пользователи не получают A/B/C. Она появляется только после этой явной операции.
Если у владельца уже есть активная программа, перенесённая A/B/C не заменяет её.

Повторный перенос возвращает прежний ID и не перезаписывает правки. После удаления
перенесённой программы сохраняется маркер импорта: повторный запуск не создаёт
её заново и возвращает None. Для сознательного повторного создания нужно другое
явное административное решение, а не автоматическое повторение команды.

Миграция v2 выполняется одной транзакцией с FK, integrity_check и
foreign_key_check до/после. Повтор v2 на готовой v2 не изменяет данных. Старая
команда v1 намеренно не стала универсальным мигратором: её повтор на v2
отклоняется, контракт v1 сохранён. Проверяйте текущую версию перед выбором команды.
На старте бот только проверяет готовую v2 и отказывается от v1/других схем.

## API программ

В `database/programs.py`:

- `create_program(user_id, name, days, activate=False)` — атомарное создание;
- `list_programs(user_id)`, `get_program(user_id, program_id)` — чтение своих;
- `update_program(user_id, program_id, name=None, days=None)` — атомарное
  редактирование, в том числе дней, упражнений, названий, порядка и подходов;
- `delete_program(user_id, program_id)` — удаление плана без удаления тренировок;
- `activate_program`, `get_active_program`, `next_day` — выбор и чередование.

Дни передаются документом: порядок элементов списка задаёт порядок выполнения.
Пустой список дней или упражнений отвергается, чтобы созданную программу можно
было использовать. Редактор Telegram пока отсутствует.

Пример структуры (user_id — внутренний ключ, не Telegram ID):

```python
days = [
    {
        "name": "Верх тела",
        "exercises": [
            {
                "exercise_id": "bench-press",  # exercises.external_id
                "name": "Мой жим",
                "warmup": [{"weight": 20, "reps": 10}],
                "working_sets": 2,
                "working_plan": [
                    {"weight": 50, "reps": 8},
                    {"weight": 55, "reps": 6},
                ],
            }
        ],
    }
]
program_id = programs.create_program(user_id, "Моя программа", days, activate=True)
```

Вместо working_plan можно указать один `working` шаблон для всех рабочих
подходов. Без веса/повторений создаются шаблоны с NULL: это указание количества,
а не требование выполнить конкретный вес.

API редактирует вложенные дни целым документом. С v4 переданные ID существующих
дней сохраняются, а курсор следует за прежним следующим днём либо его оставшимся
преемником. Новые дни без ID получают новые ключи. Снимок начатой тренировки
остаётся прежним; ссылки на удалённый источник становятся NULL. Переименование
только программы не сбрасывает курсор. Удалять последний день можно только вместе
с программой, а не сохранять пустой план. Это осознанные правила текущего API.

## Цикл дней и сохранение шага

`sessions.start_day(user_id, day_id=None)` выбирает следующий день активной
программы. Можно явно передать любой свой day_id. При завершении (включая /exit)
следующим становится день после выбранного; после последнего — первый.
Отмена не сдвигает цикл. У каждой программы свой курсор, календарь не участвует.
Если исходный день удалили во время тренировки, её завершение не двигает
новый список: действует курсор, установленный редактированием. Если день сохранил
ID, завершение выбирает его преемника в актуальном порядке дней.

В SQLite сохраняются текущая позиция, оставшиеся упражнения, очередь отложенных,
завершённые позиции и ревизия. `complete_exercise` в одной транзакции записывает
все фактические подходы, их включение и новый шаг. `postpone_exercise` сохраняет
очередь без записи подходов. Устаревшая ревизия отклоняется. Старые прямые
`save_set`/`save_exercise_sets` запрещены для тренировок со снимком, чтобы нельзя
было записать подходы отдельно от прогресса.

MemoryStorage теперь только кеширует ID тренировки/позицию/ревизию. После
перезапуска вызвать `/resume` или открыть «Тренировка»: кеш восстанавливается
из SQLite. Подтверждённый шаг не теряется даже при сбое после commit до ответа
Telegram. Если последний шаг уже завершил тренировку, она остаётся в истории.
Автоматического повторного сохранения последнего сообщения нет.

У тренировок, начатых до v2, снимка и достоверного шага нет. Они сохраняются
без изменений; доступны явные /exit или /cancel, но программа для них не
угадывается из сегодняшней A/B/C.

## Интерфейс и экспорт

Меню тренировки показывает только свои программы и дни, со страницами для
больших списков. Это выбор, а не редактор. Старые кнопки запуска A/B/C отклоняются.
История выбирается по конкретному workout_id (последние 30 завершённых записей);
старые history_A/B/C продолжают читать собственную последнюю тренировку типа.
Старые labels A/B/C не переименовываются.

В Sheets повторяющиеся упражнения различаются по настоящему set_id: для новых
строк он записывается в ранее пустую колонку F листа Sets. При желании заголовок F
можно назвать set_id. Старые строки без этого значения распознаются прежним ключом
для совместимости. Никакой реальный лист этим этапом не обновлялся. Ограничение
экспорта только первоначальным владельцем сохранено; надёжной очереди всё ещё нет.

## Оставшиеся ограничения

- Теперь редактирование доступно через Telegram-конструктор (см. EDITOR.md); AI нет.
- Снимок и прогресс имеют компактный JSON-формат; они не отдельная система FSM.
- Неподтверждённый ввод опросов по-прежнему остаётся в MemoryStorage.
- Нужен один процесс бота; сохраняется singleton. Ревизии дополнительно защищают
  от повторного применения старой кнопки/шага на уровне БД.
- Прошлые результаты одного упражнения показываются из последней своей
  завершённой тренировки, со всеми его включениями, а не угадываются по позиции
  в изменённой программе.
